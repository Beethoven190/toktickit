# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver a responsive, user-friendly Requester ticketing application. Users can select a Development Requester identity to simulate user context, submit IT support tickets with permitted attachments, inspect and filter their own tickets in "My Tickets" with strict ownership protection, open Ticket Details, add attachments, and soft-remove their own attachments with documented reasons under a unified Zen Green UI theme.

---

## 2. Stakeholder Request Interpretation
The IT department needs an MVP ticketing experience for requesters (end-users) to submit, track, and manage their support tickets. Requesters must be able to select categories, affected systems, indicate urgency/priority, attach supporting evidence, and view their submitted requests. Because full authentication will be implemented in Lab 3, a temporary Development Requester selection mechanism must be provided to switch between simulated user contexts and test multi-user ownership and isolation. The entire application must look cohesive, responsive, and follow the Zen Green design language.

---

## 3. Scope

### Included
- **Development Requester Selector:** Simulated login context selecting an active Requester, displayed in the application shell with switching capabilities.
- **Create Ticket:** Requester-facing ticket submission form capturing Category, Related System, Summary, Description, Requested Priority, and up to 5 attachments (JPG, PNG, WEBP, PDF <= 5MB).
- **Ticket Generation:** Automatic backend generation of unique official Ticket Numbers (`TKT-YYYY-XXXXXX`) with initial status `New`.
- **My Tickets View:** Paginated list of tickets owned strictly by the selected Requester, with search, category/priority/status filters, sorting, empty states, and no-results states.
- **Requester Ticket Detail:** Read-only view of ticket details and attachment management.
- **Attachment Lifecycle:** Uploading attachments to existing tickets, downloading active attachments, and soft-removing attachments with required reason retention.
- **Design System:** Implementation of Zen Green UI Theme and responsive layouts (desktop, tablet, mobile).

### Excluded
- Real authentication, login/logout credentials, passwords, sessions, and tokens (deferred to Lab 3).
- IT Staff workflow, queues, ticket claiming/reassignment, and IT Priority modification.
- Ticket collaboration, public comments, internal notes, and actions taken (deferred to later labs).
- Ticket lifecycle transitions beyond initial creation (e.g. In Progress, Resolved, Closed).
- Administrative interfaces for managing users or categories.

---

## 4. Functional Requirements
- **FR-01 (Requester Context):** The application must allow selecting any active Development Requester to establish the current user context.
- **FR-02 (Requester Switching):** The user can change the active Requester at any time, reloading user-specific data.
- **FR-03 (Reference Data Loading):** Active Categories and Related Systems must be loaded from the backend database into dropdown selectors.
- **FR-04 (Ticket Creation):** The Requester can submit a ticket with required fields (Category, Related System, Summary, Description, Priority) and optional attachments.
- **FR-05 (Ticket Identification):** Upon successful creation, the backend generates a unique official Ticket Number.
- **FR-06 (My Tickets List):** The system must display a paginated list of tickets belonging strictly to the currently selected Requester.
- **FR-07 (Search & Filtering):** Requesters can search their tickets by ticket number or summary, and filter by Category, Priority, and Status.
- **FR-08 (Sorting & Pagination):** Tickets can be sorted by creation date or ticket number, with accessible pagination controls.
- **FR-09 (Ticket Detail Retrieval):** Opening a ticket displays its full details in read-only format if owned by the current Requester.
- **FR-10 (Attachment Upload):** Requesters can attach permitted files during creation or upload additional attachments in Ticket Detail up to the limit.
- **FR-11 (Attachment Download):** Active attachments can be downloaded or previewed.
- **FR-12 (Attachment Soft Removal):** Requesters can soft-remove an attachment by providing a reason. The file content becomes inaccessible, but metadata is retained.

---

## 5. Business Rules (BR)
- **BR-01:** The official Ticket Number is generated by the backend, must be unique, and follows the format `TKT-YYYY-XXXXXX`.
- **BR-02:** Every newly created Ticket begins with Current Status `New`.
- **BR-03:** Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not real authentication.
- **BR-04:** Inactive Requesters in the database must never appear in the Development Requester selection dropdown.
- **BR-05:** Ticket Ownership Protection: A Requester can only view, search, and manage tickets that belong to their own `requesterId`. Cross-requester access via direct API or URL must return an error (403 Forbidden or 404 Not Found).
- **BR-06:** Ticket Summary is required, must not be empty after whitespace trimming, and must be between 5 and 150 characters.
- **BR-07:** Description is required, must not be empty after trimming, and must be between 10 and 2000 characters.
- **BR-08:** Requested Priority defaults to `MEDIUM` if not specified. Allowed values are `LOW`, `MEDIUM`, and `HIGH`.
- **BR-09:** Permitted attachment file types are strictly limited to `image/jpeg`, `image/png`, `image/webp`, and `application/pdf`.
- **BR-10:** Maximum attachment file size is 5 MB (5,242,880 bytes) per file.
- **BR-11:** A ticket can have a maximum of 5 active (non-removed) attachments at any time.
- **BR-12:** Attachment deletion must be implemented as soft removal (`isRemoved = true`). The record and reason are preserved, but file download and preview are strictly blocked.
- **BR-13:** A removal reason must be provided when soft-removing an attachment (minimum 5 characters).
- **BR-14:** Form validation failure must retain all entered form values so the user does not have to retype their submission.

## 6. UI Specification Summary
- **Color Palette:** Zen Green Theme — Primary green `#006B3C`, Secondary green `#0B7A46`, Pale green `#EAF6EF`, Page background `#F5F7F6`.
- **Form Controls:** Labels positioned above inputs; required fields marked with a visible red asterisk (`*`); field-level validation errors displayed directly beneath controls.
- **Button Hierarchy:** Primary green buttons for main actions (`Submit Ticket`, `Continue`); outline/secondary for secondary actions (`Cancel`, `Back`); red/danger styling for soft-removal actions.
- **Responsive Behavior:** 
  - Desktop (>= 992px): Multi-column grid, full table view for My Tickets.
  - Tablet (768px - 991px): 2-column layout for ticket forms, responsive scrollable table.
  - Mobile (< 768px): Single-column stacked fields, ticket card layout for My Tickets.

## 7. Data Changes (Prisma Schema Design)
- **`RequesterUser`:** `id`, `name`, `email` (unique), `isActive` (default: true), `createdAt`.
- **`Category`:** `id`, `name` (unique), `createdAt`.
- **`RelatedSystem`:** `id`, `name` (unique), `createdAt`.
- **`Ticket`:** `id`, `ticketNumber` (unique, indexed), `requesterId` (FK), `categoryId` (FK), `relatedSystemId` (FK), `summary`, `description`, `requestedPriority` (enum), `currentStatus` (enum, default: `NEW`), `createdAt`, `updatedAt`.
- **`Attachment`:** `id`, `ticketId` (FK), `originalName`, `storedName`, `mimeType`, `size`, `isRemoved` (default: false), `removalReason` (nullable), `removedAt` (nullable), `createdAt`.

---

## 8. API Contract Summary
- `GET /api/requesters` — Retrieve active Development Requesters.
- `GET /api/categories` — Retrieve available ticket categories.
- `GET /api/systems` — Retrieve available related systems.
- `POST /api/tickets` — Create a new ticket with validated fields.
- `GET /api/tickets` — Retrieve paginated tickets owned by `requesterId` with query params `search`, `category`, `priority`, `status`, `page`, `limit`.
- `GET /api/tickets/:id` — Retrieve single ticket details with ownership validation.
- `POST /api/tickets/:id/attachments` — Upload attachment for a ticket.
- `GET /api/tickets/:id/attachments/:attachmentId/file` — Download active attachment file.
- `DELETE /api/tickets/:id/attachments/:attachmentId` — Soft-remove attachment with reason.

## 9. Acceptance Criteria (Given-When-Then)
- **AC-01:** Given valid ticket form data, when the Requester submits the form, then the ticket is saved with status `NEW` and the official Ticket Number (`TKT-YYYY-XXXXXX`) is returned and displayed.
- **AC-02:** Given no Development Requester is selected, when the user visits ticket screens, then the Requester Selection screen is displayed.
- **AC-03:** Given Requester A is active, when Requester A views My Tickets, then only tickets belonging to Requester A are returned.
- **AC-04:** Given Requester B attempts to open a ticket owned by Requester A, then the backend rejects the request with an authorization/ownership error.
- **AC-05:** Given an attachment larger than 5 MB or of an unsupported mime-type (e.g. `.exe`), when upload is attempted, then a validation error is returned and upload is rejected.
- **AC-06:** Given an active attachment on an owned ticket, when the user confirms soft removal with a reason, then `isRemoved` becomes true, the reason is recorded, and download attempts return 404/410.
- **AC-07:** Given a search keyword, when the Requester filters My Tickets, then only matching tickets owned by that Requester are displayed.

## 11. Assumptions and Decisions
1. **Ticket Number Format:** Selected `TKT-YYYY-XXXXXX` where `YYYY` is the current year and `XXXXXX` is a 6-digit zero-padded sequential or random unique number.
2. **Storage of Attachments:** Local disk storage in `server/uploads/` with UUID-based stored filenames to prevent filename collisions and directory traversal attacks.
3. **Soft-Removal Security:** File binary is preserved on disk or unlinked per retention policy, but API layer immediately treats `isRemoved = true` as non-downloadable.
